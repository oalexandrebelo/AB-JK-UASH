# Revisão SDK, API e fiscal — 2026-10-21

Revisão local do AB-UASH 0.2.1, executada com Node.js 24.19.0. O objetivo foi verificar o contrato público, a preservação de valores e o comportamento após perda de resposta fiscal. Os testes usaram SQLite temporário, HTTP em loopback e transportes fiscais de fixture; nenhuma NFS-e foi enviada a um provedor externo.

## Correções

| Falha reproduzida | Comportamento corrigido | Evidência |
| --- | --- | --- |
| O SDK aceitava `ok:false` com HTTP 2xx como erro confirmado da API; `AUTH_REQUIRED` nesse envelope também limpava a sessão | Status HTTP e `ok` precisam concordar. Contradição produz `TransportError(kind: protocol)` e mantém a sessão local | Regressão SDK de envelope contraditório |
| A validação por expressão regular convertia números e objetos para texto, permitindo uma chave preparada cujo objeto poderia mudar depois | Chave idempotente e token de setup exigem strings antes de qualquer envio | Regressão JavaScript de chave/token coercível |
| O schema da folha limitava agregados brutos ao teto de cada lançamento | Agregados de salário, comissão, acréscimos e descontos, incluindo comissão de uma linha, admitem inteiros seguros. Entradas e total líquido mantêm seus limites | HTTP real: base de 1,6 bilhão de centavos, descontos de 1,8 bilhão e líquido de 200 milhões; outro caso acumula comissão de 1,2 bilhão em uma linha |
| O snapshot fiscal ordenava serviços pelo UUID, divergindo da ordem da OS | Snapshot e descrição automática seguem `position,id` | UUIDs deliberadamente em ordem inversa; valores de serviço e desconto conferidos em centavos |
| Resposta fiscal HTTP 4xx com estado de autorização ou processamento era marcada como rejeitada e liberava a ordem para outro rascunho | Estados de processamento, documento existente ou estado desconhecido em resposta contraditória permanecem `uncertain`. Novo rascunho é bloqueado; reconciliação usa a referência original | Fixture 422 com `autorizado`, replay local e GET de reconciliação; exatamente um POST |
| Replay de operação sem resposta gravada retornava HTTP 202 mesmo quando outro worker já havia reconciliado o rascunho como autorizado | Replay lê o estado corrente e usa HTTP 200 para desfecho terminal ou 202 para pendência/incerteza | Expiração de lease, conclusão por GET, resposta tardia e replay; nenhum segundo POST |

As seis regressões iniciais falharam contra a implementação anterior e passaram após as correções. Foi acrescentado um sétimo teste específico para comissão acumulada por linha.

## Validação executada

`npm run sdk:build` terminou com sucesso e regenerou o OpenAPI e os artefatos do SDK.

Comando de validação final:

```sh
node --test --test-reporter=tap \
  tests/sdk.test.mjs \
  tests/sdk-contract.test.mjs \
  tests/sdk-types.test.mjs \
  tests/sdk-review-20261021.test.mjs \
  tests/fiscal.test.mjs \
  tests/fiscal-transport.test.mjs \
  tests/fiscal-review-20261021.test.mjs
```

Resultado: **43 testes aprovados, zero falhas, zero ignorados**. A contagem inclui seis subtestes de transporte. A suíte de contrato percorreu **97/97 operações** por HTTP real com SQLite, incluindo os seis formatos de relatório. A suíte TypeScript validou assinaturas, erros de compilação esperados e o exemplo de navegador. O relatório TAP está em `TEST-RESULTS-review-20261021.txt`.

Também foram verificadas paginação vazia e paginação no limite de uma linha, rejeição de entrada monetária acima do limite, replay de pagamento sem duplicação, timeout durante o corpo da resposta, DNS fixado, bloqueio de redirecionamento, expiração de lease, reinício e falha de persistência do resultado fiscal.

## Limites desta revisão

Esta execução não comprova homologação fiscal, conformidade tributária de uma empresa, credenciais reais do provedor, emissão em produção, implantação no MacMini/AB-SRV ou paridade com Jumpcar. O contrato fiscal continua exigindo revisão tributária explícita. A autenticação e a observação direta do Jumpcar pertencem ao fluxo autorizado de navegador, fora desta frente.

Não foram executados testes PostgreSQL nesta frente. Os testes fiscais usam o adaptador compartilhado que permite essa execução, mas o resultado registrado aqui é de SQLite. Os testes de SDK também usaram SQLite.
